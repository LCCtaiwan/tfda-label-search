# Pagefind 容量試驗

## 試驗目的

確認純靜態網站在 1,000 至 5,000 份仿單時，仍可放入 GitHub Pages 類型的空間，並可在桌機與手機瀏覽器正常搜尋。

## 資料限制

本次沒有大量呼叫 TFDA API。測試資料是把一份既有的真實 TFDA 結構樣本複製成不同藥證與藥名，再明確標示為 `synthetic_capacity_fixture`。它可測容量、檔案數及基本速度，但不能代表全臺仿單的長短差異、涵蓋率或搜尋品質。

產生器限制最多 5,000 份，避免不小心製造無上限資料：

```sh
npm run fixture:capacity -- \
  --source tests/fixtures/structured-real-sample.json \
  --output output/capacity/5000-documents.json \
  --documents 5000
```

`output/` 已由 Git 忽略，不會把大型測試檔提交到原始碼庫。

## 被淘汰的第一版

第一版把每個仿單章節各做成一筆 Pagefind 記錄。1,000 份仿單、50,000 個章節的結果如下：

| 項目 | 結果 |
|---|---:|
| 建置時間 | 78.83 秒 |
| 網站大小 | 217 MB |
| Pagefind 大小 | 202 MB |
| 全部檔案數 | 52,242 |

這個做法若放大到 5,000 份會過於龐大，因此判定不通過並淘汰。

## 採用的壓縮架構

現在每份仿單只建立一筆 Pagefind 候選索引。使用者查詢後，瀏覽器只下載候選藥品的乾淨 JSON，再逐章做精確的 AND、OR、NOT 與人工同義詞判斷。結果每次顯示 50 筆，可按「載入更多結果」繼續查看。

| 測試量 | 章節數 | 建置時間 | 網站大小 | Pagefind | 資料 JSON | 全部檔案數 |
|---:|---:|---:|---:|---:|---:|---:|
| 1,000 份 | 50,000 | 5.84 秒 | 21 MB | 4.9 MB | 16 MB | 2,111 |
| 5,000 份 | 250,000 | 29.24 秒 | 100 MB | 22 MB | 78 MB | 10,336 |

相較第一版，1,000 份網站由 217 MB 降為 21 MB，約減少九成。以上時間是單次本機量測，不是所有電腦或 GitHub Actions 的保證值。

## 真實瀏覽器結果

使用 Chromium 在本機 HTTP 伺服器查詢：

| 測試量 | 第一次查常見詞「懷孕」 | 重複查「懷孕」 | 查單一藥名／編號 |
|---:|---:|---:|---:|
| 1,000 份 | 520 ms | 92 ms | 140 ms |
| 5,000 份 | 864 ms | 191 ms | 724 ms |

- 常見詞先顯示 50 筆；實際點擊「載入更多」後可正確增加到 100 筆。
- 390 × 844 手機畫面通過目視檢查。
- 瀏覽器主控台為 0 錯誤、0 警告。

## 結論與未完成事項

5,000 份合成資料的容量與本機速度通過，純靜態架構可繼續使用，不需要為了這個規模先建立 Supabase 或 Cloudflare D1。

正式發布前仍需在 TFDA 確認可接受的批次頻率後，以 1,000 至 5,000 份具有不同長度的真實仿單重做搜尋品質、涵蓋率及容量驗證。合成測試不能取代這一步。
